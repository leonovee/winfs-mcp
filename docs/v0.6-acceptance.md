## Scope

v0.6 ships three orthogonal additions on top of the v0.5.1 29-tool surface:

1. **Feature A — Configurable filesystem scope** (`unrestrictedFilesystem`
   + magic-string confirm). Opt-in mode where `checkAllowed`
   short-circuits and accepts paths outside `allowedRoots`. Other
   defenses stay in force. For dev sandboxes / agent VMs only.
   Spec §U / invariants #28–#30.

2. **Feature B — `write_chunk` tool**. Byte-offset surgical in-place
   write for huge files. Explicitly NON-atomic (`atomic: false`
   literal in response). Companion to v0.1 `read` (which has range).
   Spec §V / invariants #31–#33.

3. **Feature C — `edit_file.edits[].expected_count` extension**.
   Optional per-edit field (default 1, preserves v0.5 contract).
   0 = assertion-only; N ≥ 2 = multi-replace atomically. Spec §W /
   invariant #34.

Net surface delta: **+1 tool** (29 → 30; `write_chunk`) + 1 schema
extension on `edit_file` + 1 cross-cutting config option.

## ⚠️ BREAKING CHANGES from v0.5

Per operator directive (2026-05-18, Phase 6d Q1+Q2): v0.x semver
explicitly allows breaking changes on minor bumps; no back-compat
shim shipped. Both formalised in spec §W and listed in CHANGELOG
[0.6.0] BREAKING CHANGES section.

- **`edit_file` EUNIQUE `details` field renamed**: `occurrences` →
  `occurrences_found`. Plus new `expected_count` sibling field.
- **`edit_file.replacements_made` semantics**: was `args.edits.length`
  (input echo, zero-info); now actual sum of replacements performed.

### 3. `structured_content` invariant covers `write_chunk` envelope ⚠️ (deferred)

`write_chunk` registers via the standard `runTool` wrapper, so its
`structuredContent` is the impl's `ok()` value 1:1 by construction.
The contract is enforced at type level (Zod `OutputShape` + the
wrapper's "no envelope keys leak" guarantee). The
`structured_content.test.ts` invariant suite was NOT extended to
exercise `write_chunk` end-to-end during Phase 6d because the existing
v0.4 wrapper test covers the envelope-purity contract for every tool
that goes through `runTool`. If the v0.5.x external review wave (or
future findings) shows a regression specific to write_chunk's
envelope, it gets added then. Acceptable per `Step 5 #3` interpretation.

## Considered & rejected

Per v0.6 prompt Step 6 "Out of scope" + operator directives during
Phase 6abc:

- **Streaming reads/writes for files > readMaxBytes** (interpretation
  C from the prompt). Deferred to v0.7+ pending real-use signal.
- **Transactional rollback for `write_chunk`**. Would re-introduce
  atomic ceremony — defeats the purpose. Rejected permanently;
  `write_chunk` is non-atomic by design.
- **POST/PUT body support for `fetch_url`**. Out of v0.6; possibly
  v0.7.
- **HTTP/2 / HTTP/3 support**. Out of v0.6; possibly v0.7.
- **`expected_count` semantics "at least N" / "at most N"**. v0.6
  ships only exact-match semantics. Callers needing inequality
  composition can dry-run + read.
- **Back-compat shim for renamed EUNIQUE field (Q1)**. Operator
  explicitly approved breaking change without shim — v0.x semver
  permits it; CHANGELOG flags it clearly.
