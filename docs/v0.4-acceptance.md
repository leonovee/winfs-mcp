## Scope

v0.4 closes spec §7 row "**Editor + Slicing + Diff + Incremental tail**" — Claude
can modify code without dropping to a shell, slice large files without blowing
context, watch logs/output incrementally, and compare two versions textually.

4 new tools:

- `read_section` — line / byte range slicing with UTF-8 boundary trim
- `diff_files` — unified textual diff (file or inline, two formats)
- `edit_file` — atomic find-and-replace with `dry_run` + uniqueness invariant
- `read_since` — incremental tail with rotation detection

Spec amendments §I–§L formalise the contract for each.

### 3. structured_content invariant covers all 4 new envelopes ✅

Pure-payload check added for each new tool. Asserts the exact key set of
`structuredContent` matches the declared `outputSchema`:

- `read_section` → `{content, encoding, range, total_bytes, total_lines}` (line_range path)

- `read_since` → `{content, file_rotated, mtime, new_offset, total_bytes, truncated}`

### 4. `tests/invariants/edit_file_atomic.test.ts` exists and passes ✅

Two cases pin spec amendment §I:

- **`dry_run` does NOT create temp file.** `fs.readdir(root)` before and after
  match; the file's contents are unchanged. Confirms the impl forks before
  the atomic-write path.
- **`fs.rename` failure leaves the original intact.** Monkey-patched
  `fs.rename` throws `EBUSY`; the impl surfaces `EBUSY` to the caller;
  `fs.readFile` of the original target still returns the pre-edit content;
  no `.tmp` orphan remains in the directory (atomic_write.ts unlinks on
  rename failure).

## Hard invariants reaffirmed in v0.4

All v0.1 + v0.2 + v0.3 invariants still hold. v0.4 adds three more:

- **`edit_file` uniqueness invariant.** Each `old_str` MUST appear exactly once.
  Pinned by 3 unit tests (0×, 2+×, sequential cascade).
- **`edit_file` dry-run leaves no temp artifact.** Pinned by an invariant test
  that `readdir`s the parent dir before and after.
- **Audit log redacts `edit_file` edits (sensitive-array semantics).**
  `sanitizeArgs` now treats arrays at sensitive keys as `<redacted: N items>`.

## Considered & rejected

- **`edit_file` with regex matching.** Footgun + CPU bomb potential; would ship
  as a separate tool with opt-in danger flag if ever needed. Out of v0.4.
- **`edit_file` line-based addressing.** Line numbers drift across edits; the
  `old_str` uniqueness invariant is the safer primitive.
- **`read_section` marker-based slicing.** Original spec §4.5 design. Pivoted
  to range-based per amendment §J (rationale recorded there: marker-based
  blurs into `grep` territory; range-based composes with
  `read_multiple_files`).
- **`diff_files` three-way / patch application.** Future scope (`apply_patch`
  or similar in v0.5+). v0.4 is read-the-difference only.
- **`read_since` with mtime cursor.** Byte offset is exact + rotation-detectable;
  mtime is fuzzy and breaks on filesystem-resolution boundaries.
