### 5. Allowed-roots работает ✅

Verified by `tests/invariants/allowed_roots.test.ts` and
`tests/unit/fs/read.test.ts > 'returns EPERM_ROOT for a path outside
allowedRoots'`. Probe target `C:\Windows\System32\drivers\etc\hosts`
resolves to a real path that is not under any `allowedRoots` entry; the
result is `EPERM_ROOT` with the `allowedRoots` list echoed in the `hint`.

A **non-existent** path outside the sandbox also returns `EPERM_ROOT`
(not `ENOENT`) — eliminates an existence-leak channel. See the
`security` note in `CHANGELOG.md` and the test
`tests/unit/fs/append.test.ts > 'returns EPERM_ROOT outside allowedRoots'`
(target path `C:\Windows\test.log` does not exist, must still return
`EPERM_ROOT`).

### 6. Timeout работает ✅

`tests/invariants/timeouts.test.ts > 'resolves with ETIMEDOUT when task
exceeds deadline'` runs a 5000 ms simulated hang against a 100 ms
deadline. Result returns inside 1 s with `code: "ETIMEDOUT"`. The signal
is aborted so cooperative cancellation works.

For the spec's "huge file" example, `tests/unit/fs/read.test.ts >
'returns ETOOLARGE when file size exceeds max_bytes'` covers the size-cap
path (which fires before the timeout for any realistic case).

### 7. UTF-8 round-trip ✅

`tests/invariants/utf8.test.ts > 'write→read roundtrips Russian + emoji +
ASCII identically'` writes
`Привет, мир\n🚀 emoji line\nplain ASCII\nспецсимволы: ёщъыЁ\n`,
re-reads it, asserts byte-identical, and asserts the written file does
not start with the UTF-8 BOM (`0xEF 0xBB 0xBF`).

### 8. Realpath escape blocked ✅

`tests/invariants/allowed_roots.test.ts > 'symlink/junction escape
outside allowed root is blocked'` creates a real symlink inside the
allowed root that points to a directory **outside** any allowed root,
then attempts to read through it. Result: `EPERM_ROOT`.

(On Windows the symlink creation requires Developer Mode or admin
elevation; the test skips itself with platform detection if creation
returns `EPERM`/`EACCES`, so CI on a non-elevated runner still passes
without lying.)

The `..`-escape variant is covered by the same file's first test.

### 9. Audit log пишется ✅

`tests/invariants/audit.test.ts > 'writes JSONL records to the configured
audit path'` invokes `appendAudit` twice (one `ok`, one `error`) and
asserts both records appear as valid JSONL at
`config.resolvedAuditLogPath`. The `'redacts the content field'` test
asserts spec §2.11's redaction contract (content body → `<redacted: N
bytes>`).

## Quality checklist (from `node_mcp_server.md`)

The reference's checklist is reproduced below with v0.1 status. Items
N/A to a v0.1 slice (resources, HTTP transport, pagination at scale)
are marked accordingly.

### Strategic Design

- [x] Tools enable complete workflows — read/write/append/list/stat is the
      minimum useful FS surface for an architect agent.
- [x] Tool names reflect natural task subdivisions.
- [x] Response formats optimise for agent context efficiency —
      `structuredContent` + short JSON in `content[]`.
- [x] Human-readable identifiers used where appropriate (ISO mtimes,
      octal mode strings).
- [x] Error messages guide agents toward correct usage — `hint` field on
      `EPERM_ROOT` echoes `allowedRoots`, `EEXIST` suggests
      `overwrite=true`, `ETOOLARGE` shows the current limit.

### Implementation Quality

- [x] FOCUSED IMPLEMENTATION — v0.1 scope frozen to 5 tools, no
      pre-emptive v0.2+ code.
- [x] All tools registered via `registerTool` with complete configuration.
- [x] All tools include `title`, `description`, `inputSchema`, and
      `annotations`.
- [x] Annotations correctly set (read/list/stat are
      `readOnlyHint: true, idempotentHint: true`; write/append carry the
      correct `destructiveHint`).
- [x] All tools use Zod schemas for runtime input validation. `.strict()`
      is applied at `InputSchema` even though the SDK consumes the
      `InputShape` form — `InputSchema.parse()` is available for tests
      and any direct callers.
- [x] All Zod schemas have constraints and descriptive `.describe()`
      strings.
- [x] All tools have comprehensive descriptions with explicit input/output
      contracts and error catalogue per tool.
- [x] Error messages are clear, actionable, and educational.

### TypeScript Quality

- [x] Interfaces defined for all tool result types.
- [x] `"strict": true` in `tsconfig.json` with extra
      `"noImplicitOverride"` and `"noFallthroughCasesInSwitch"`.
- [x] No untagged `any`. One explicit widening cast remains in
      `tool_wrapper.ts` after the timeout race — flagged inline.
- [x] All async functions have explicit `Promise<T>` return types.
- [x] Error handling uses proper type guards (`NodeJS.ErrnoException` cast
      pattern in `fromNodeError`).

### Advanced Features

- [ ] Resources — N/A for v0.1. Spec §4 has no resource-based tools.
- [x] Transport — stdio configured per spec §1.
- [ ] Notifications — N/A. Tools list is static at v0.1.

### Project Configuration

- [x] `package.json` includes all dependencies.
- [x] Build script produces `dist/index.js`.
- [x] Main entry `dist/index.js`.
- [x] Server name `mcp-winfs`. (Spec uses an unprefixed name because
      this is a single-purpose user-facing server, not a service
      integration.)
- [x] `tsconfig.json` in strict mode.

### Code Quality

- [ ] Pagination — N/A. `list` enforces depth ≤ 5 but does not offset.
      Added in v0.3 alongside `grep`.
- [x] Large responses — `read` honours `readMaxBytes` and reports
      `truncated:true`. `list` is depth-capped.
- [ ] Filtering for large result sets — `list` accepts `glob`. v0.3
      adds `grep` filtering.
- [x] Timeouts on all network/I/O — every tool runs inside `runTool` ->
      `withTimeout`.
- [x] Common functionality extracted — `runTool`, `checkAllowed`,
      `encodeUtf8NoBom`, `atomicWriteFile` are reused across tools.
- [x] Return types consistent (`Result<T>` for impls, `ToolResponse` for
      handlers).

### Testing and Build

- [x] All imports resolve.
