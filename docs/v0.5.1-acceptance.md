release the spec §4 tool surface is complete at **29 tools**; v1.0 remains for MCPB
packaging + evals harness + production README rewrite — no new tools.

11 new tools across 4 surfaces:

**Git read-only (5)** — §4.6
- `git_status` — porcelain parse → `{branch, ahead, behind, staged, modified, untracked, conflicted}`
- `git_log` — multi-commit parse with optional range / path_filter / count cap
- `git_show` — single sha (hex only) → `{sha, author, email, date, message, diff, files_changed}`
- `git_diff` — `rev_a`..`rev_b` (defaults to `HEAD` / worktree) with stats
- `git_blame` — file blame with line-range cap (10000 entries) → `{blame, total}`

**Exec (3)** — §4.7
- `execute_command` — PowerShell dispatch with hardcoded blocklist + bounded I/O + sanitized PATH + process tree kill
- `run_python` — `{mode: "inline"|"file", script}` against `<config.pythonHome>/python.exe`
- `run_pytest` — summary-line parser (`X passed, Y failed, Z skipped`) with collect-only mode

**System (2)** — §4.8
- `find_command` — `Get-Command`-backed lookup, optional `with_version` invocation
- `check_env` — safe-prefix only (`{present, length, prefix[0:4]}`); invariant #8 strictly bounded

**Network (1)** — §4.9
- `fetch_url` — two-layer SSRF defense (host whitelist → DNS resolve → IP deny → connect-by-IP + Host header rewrite); 5 MB / 15 s hard caps; HTTP/1.1 GET only; 3-redirect chain with per-hop re-validation

Spec amendments §N–§T formalise the contracts.

## Hard invariants reaffirmed in v0.5

All v0.1 + v0.2 + v0.3 + v0.4 invariants still hold. v0.5 adds:

- **Git mutation-flag hard-deny.** `src/core/git_safety.ts` denylist applied
  pre-spawn. No `--commit` / `--push` / `--reset` / `--checkout` / `--rebase`
  reaches the git binary. Hardcoded, not config-driven (invariant #12 — no
  runtime mutation). Pin: §N.
- **Exec blocklist (additive-only config).** `src/core/exec_safety.ts` ships 9
  default regexes per spec §2 #7. Operator can ADD patterns via
  `config.execExtraBlocklist` but cannot REMOVE defaults. Pin: §O.
- **PATH sanitization for subprocess spawn.** Minimal inherited PATH
  (`System32`, `Windows`, `Git\cmd`, `nodejs`, optional `pythonHome`). User
  shims / aliases never reach exec children. Pin: §P.
- **`check_env` mathematical safe-prefix bound.** Implementation:
  `prefix = value.length >= 4 ? value.slice(0, 4) : ""`. Adversarial unit test
  pins the upper bound; no caller can extract > 4 chars regardless of args. Pin: §Q.
- **`fetch_url` two-layer SSRF defense.** Layer 1 host whitelist (pre-DNS).
  Layer 2 DNS resolve + IP deny (post-DNS). Connect-by-IP with manual `Host:`
  header rewrite closes DNS rebinding TOCTOU. Pin: §R.
- **`fetch_url` redirect chain re-validation.** Each of up to 3 redirect hops
  re-validated through Layer 1 + Layer 2. `final_url` in response shows last
  destination. Pin: §S.
- **Audit redaction extensions.** `execute_command.args` last-64-chars per arg;
  exec stdout/stderr 4 KB cap with `truncated_at: N`; `run_python.script` first
  256 chars; `fetch_url.url` query string redacted past `?`; `check_env` values
  never logged. Pin: §T.

## Considered & rejected

- **`execute_command` via cmd.exe.** PowerShell-only dispatch keeps dialect
  surface to one. cmd.exe quoting and `^` escape rules are a known footgun
  vector; folding both in would multiply attack surface for marginal benefit.
- **`run_python` PATH-resolved binary.** Closed Python-shimming attack vector.
  `<config.pythonHome>\python.exe` is the only resolution path; PATH lookup
  intentionally disabled.
- **`fetch_url` with request body.** GET-only in v0.5. POST/PUT body invariants
  (CSRF tokens, content-type sanity) deferred to v0.5.x if real-use surfaces.
- **`fetch_url` HTTP/2 / HTTP/3.** Node `http`/`https` is HTTP/1.1; adding
  `http2` would expand wire-format surface without clear demand.
- **`fetch_url` caller-controlled `Authorization` / `Cookie` headers.** Closes
  credential-leak vector via response logging or audit. Whitelist of safe
  headers: `User-Agent`, `Accept`, `Accept-Language`.
- **Runtime config mutation (`block_command(pattern)` / `whitelist_url(host)`).**
  Spec invariant #12 absolute. All config changes through restart. Blast-radius
  limit.

## Known issues — v0.5.1 patch wave

### P1 — `run_python` silent spawn-failure

When `python.exe` is not resolvable on the sanitized PATH (or
`config.pythonHome` is unset/wrong), `run_python` returns
`{exit_code: null, stdout: "", stderr: "", duration_ms: ~10, isError: false}`
instead of a structured error `EPYTHONNOTFOUND`. The `isError: false`
shape masks the failure from callers — they see a "successful run with
no output" rather than a typed error code.

Surfaced at Inspector smoke probe #25. Operator decision (2026-05-17):
ship v0.5.0 with this bug per `prompts/cc-prompt-v0.5-execute-fastpath.md`
§90 risk acknowledgement. Mitigated: `run_pytest` (which calls into
similar plumbing) already handles EPYTHONNOTFOUND gracefully; callers
using `run_pytest` are not affected.

Fix in v0.5.1: catch spawn-error in `run_python.ts`, return
`buildError("EPYTHONNOTFOUND", "python binary not found", { details: { cause, errno, resolved_path } })`.
Add unit test exercising the missing-binary path. Add to invariant
suite to prevent regression.

### P2 — `execute_command` silent output capture for `&`-operator invocations

When `execute_command` is invoked with a PowerShell `& "C:\path\with spaces\exe.exe" args...`
call pattern, stdout and stderr from the child process do NOT propagate to
the captured response. The command DOES execute correctly (state changes
land on disk / network — empirically verified by `git tag -a v0.5.0` and
`git push origin main` both succeeding from server-side calls despite empty
returned output), but caller cannot observe results.

Symptom shape from server side: `{stdout: "", stderr: "", exit_code: 0, duration_ms: ~134, truncated_*: false, timed_out: false}` —
identical 134ms duration for divergent commands strongly suggests the
PowerShell wrapper closes/doesn't pipe child-of-child stdio in the
`-NoProfile -NonInteractive` mode used by execute_command.

Surfaced at v0.5.0 release-tag operation (chat Claude tried to push via
winfs:execute_command — git ops executed but no output captured for
verification).

Severity P2 (not P1) because:
- Commands do execute correctly (state mutation works)
- Workaround exists: caller invokes git directly via shell, or uses
  plain `git status` style (without `&` operator) when binary is on
  the sanitized PATH

Fix candidates in v0.5.1:
- Investigate Node `spawn()` stdio inheritance through PowerShell's `&` call operator
- Test `PowerShell -Command 'git status'` vs `PowerShell -Command "& 'git.exe' status"` — which preserves stdio?
- Consider Start-Process with `-RedirectStandardOutput`/`-RedirectStandardError` to explicit temp files, then read those

### P2 — Methodology drift in `prompts/cc-prompt-v0.5-inspector-smoke.md`

Five arg-shape mismatches between methodology and actual schemas
(surfaced at Inspector smoke):

- `read_json` output field is `data`, methodology said `value`
- `git_show` requires hex sha, methodology used symbolic `HEAD`
- `git_blame` requires absolute path, methodology used relative `package.json`
- `run_python` args shape is `{mode, script}`, methodology used `{args: [...]}`
- `read_section` uses `line_range` / `byte_range`, methodology used marker fields (per amendment §J — see next item)

Doc-only fix in v0.5.1; methodology corrections will be reflected in the
prompt before next Inspector smoke (Phase 4f for v0.5.x / v0.6).

### P2 — `read_section` spec §4.5 vs amendment §J prose inconsistency

Spec §4.5 describes `read_section` with marker-based slicing
(`start_marker`, `marker_type: "md_heading" | "regex"`). Amendment §J
(landed in v0.4) supersedes §4.5 with range-based slicing (`line_range`,
`byte_range`) — impl is correct per §J.

The prose inconsistency in the spec body (§4.5 wording remains visible per
append-only amendment convention) caused the Inspector smoke methodology
prompt to reference §4.5 directly without picking up §J. Not an
impl gap.

Fix in v0.5.1: spec body consolidation pass — either inline an amendment-cross-reference
arrow `(§4.5 → §J)` in §4.5 prose, OR rewrite §4.5 in-place with redirect
note to §J. Operator's call which convention scales.

### P2 — R9 process-tree methodology weakness

`execute_command` timeout test uses `Start-Sleep -Seconds 30` which
self-terminates regardless of process-tree-kill correctness. Even a
failed tree kill would show no orphan by check time. Methodology fix in
v0.5.1: replace with infinite-loop child (`while($true) { Start-Sleep 1 }`)
that wouldn't exit without explicit kill — proper tree-kill verification.

### P2 — R13 check_env cross-verify methodology limitation

Safe-prefix cross-verify requires reading `$env:PATH.Length` and
`$env:PATH.Substring(0,4)` in the **same PowerShell session where
Inspector was spawned** — not any external shell. Inspector inherits
spawn-time env; verification shell may have different PATH.

At smoke time: Inspector reported `length=1954, prefix="C:\U"`. External
verify shell reported `length=1507, prefix="C:\W"`. Divergence explained
by different inherited PATHs (Inspector spawned from VS Code terminal
/ npm-activated shell with user-bin paths first; verify shell had
standard system path first). Wire-level invariant
`prefix.length === 4` ✓ satisfied.

Methodology pin in v0.5.1: capture spawn-time `$env:PATH` snapshot
before launching Inspector for cross-verification source.

### P3 — `find_command(name: "git")` returns `found: false` despite git being on standard install path

In v0.5.0, `find_command` invoked from within the server (e.g. through
winfs:execute_command meta-loop) returns `{found: false}` for `git`.
External PowerShell `Get-Command git` succeeds, returning
`C:\Program Files\Git\cmd\git.exe`. Likely cause: sanitized PATH for
subprocess spawn does NOT include `C:\Program Files\Git\cmd` despite
spec invariant #10 listing it. Either impl deviated from spec (excluded
git path), or installation has git elsewhere.

Surfaced when chat Claude tried git operations via winfs:execute_command
post-tag — `git` command failed with "not recognized" until invoked
via absolute path `& "C:\Program Files\Git\cmd\git.exe"`.

Severity P3: workaround exists (use absolute path for git); does not
affect callers who pre-pend git directory to PATH or who use git tools
directly (`git_status`, `git_log`, etc., which use git binary discovery
through a different code path).

Fix in v0.5.1: audit `exec_safety.ts` PATH sanitization list against
spec invariant #10, ensure `C:\Program Files\Git\cmd` (or wherever
git is installed per system probe) is included; add invariant test
that pins the PATH list against spec.
