## Symptom (observed throughout the 2026-05-22 session)

- Intermittent `No result received … after waiting 4 minutes` on winfs tool
  calls from chat-Claude / Claude Desktop (`winfs:write` of large prompts,
  `winfs:read`, `execute_command`).
- Recovery pattern: 2–3 four-minute timeouts on the *same* call, then the next
  call goes through instantly.
- Most reliable trigger this session: a large `winfs:write` (~10 KB payload).

## The two log sources

### A. winfs-side — this wave's instrumentation

Set `WINFS_TRANSPORT_LOG=<path>` in the winfs launch env. winfs then appends
**metadata only** (never bodies):

```
<ISO ts> RECV <id> <method> <bytes>
<ISO ts> SEND <id> <status> <bytes> <duration-ms>
```

- `RECV` = winfs read the request off stdin. `SEND` = winfs finished
  processing and is about to write the response to stdout (logged *before* the
  wire write, so it survives an outbound-pipe stall).
- `duration-ms` = winfs processing time (RECV→SEND) for that id.

### B. Claude Desktop-side — CD's own MCP log

`%APPDATA%\Claude\logs\` (on this machine:
`C:\Users\Expert\AppData\Roaming\Claude\logs\`):

- `mcp-server-winfs.log` — per-server, winfs only.
- `mcp.log` — combined across all MCP servers (filter lines containing `[winfs]`).

Format (per-server file):

```
<ISO ts> [winfs] [info] Message from client: {"jsonrpc":"2.0","id":N,"method":"…",…}
<ISO ts> [winfs] [info] Message from server: {"jsonrpc":"2.0","id":N,"result":…}
```

- "Message from client" = CD handed the request to winfs's stdin (CD-dispatch).
- "Message from server" = CD read the response off winfs's stdout (CD-receive).
- **CD logs full bodies** (request args, response content — file contents,
  command output, paths). That is CD's log, not ours; our `WINFS_TRANSPORT_LOG`
  deliberately logs none of it. When attaching excerpts to an upstream report,
  redact bodies from the CD log.

### Clock note

CD spawns winfs as a local child process — **both logs use the same system
clock**, so the four timestamps below are directly comparable with no
skew correction.

## The 4-point timeline

For any single request `id`, join the two logs and read off four timestamps:

| Point | Source | Meaning |
|-------|--------|---------|
| `t1` | CD `Message from client` ts | CD wrote the request to winfs's stdin |
| `t2` | winfs `RECV <id>` ts | winfs read it off stdin |
| `t3` | winfs `SEND <id>` ts | winfs finished, about to write stdout |
| `t4` | CD `Message from server` ts | CD read the response off winfs's stdout |

Per-leg latency:

```
inbound  = t2 - t1     CD → winfs   (stdin delivery)
process  = t3 - t2     winfs work   (P3: should be fast, < ~250 ms)
outbound = t4 - t3     winfs → CD   (stdout delivery + CD pickup)
```

A ~240 s (4-minute) stall localizes to whichever leg carries the gap.

## Phase C — reproduction protocol (operator: Vladimir / chat-Claude)

1. **Enable winfs logging.** In Claude Desktop's `claude_desktop_config.json`,
   add an `env` entry to the winfs `mcpServers` block:

   ```json
   "winfs": {
     "command": "node",
     "args": ["C:\\Users\\Expert\\Desktop\\AI\\tools\\winfs\\dist\\index.js",
              "--config", "…\\configs\\local.json"],
     "env": { "WINFS_TRANSPORT_LOG": "C:\\Users\\Expert\\Desktop\\AI\\tools\\winfs\\.transport.log" }
   }
   ```

   (Pick any writable path. The file is created on first event.)

2. **Restart Claude Desktop fully** — tray → Exit (not just close the window) →
   relaunch — so winfs is respawned with the new env. Confirm on stderr /
   in `mcp-server-winfs.log` that winfs printed
   `transport logging ON → <path>`.

3. **Trigger the hang** from a chat-Claude session: issue the operation that
   stalls — a large `winfs:write` (~10 KB payload was the most reliable
   trigger). Repeat until a 4-minute timeout fires.

4. **Mark wall-clock time** when chat-Claude reports the 4-minute timeout.

5. **Capture, around that timestamp:** the winfs transport log
   (`WINFS_TRANSPORT_LOG`), and the CD log
   (`%APPDATA%\Claude\logs\mcp-server-winfs.log`). Note the JSON-RPC `id` of the
   hung call if visible (it is the next id after the last successful response).

Then run the correlation tool (Phase D) over the two captured logs.

## Phase D — correlation analysis

Tooling: `scripts/analyze-transport-hang.mjs` (added this wave). Usage:

```
node scripts/analyze-transport-hang.mjs <winfs-transport.log> <CD mcp-server-winfs.log>
```

It joins the two logs by request id and prints, per id, the four timestamps
and the three per-leg latencies, flagging any leg above a threshold (default
5 000 ms). For the hung id, read which leg carries the multi-second gap.

Decision tree (fill in once a hang is captured):

- **No `RECV <id>` in the winfs log** → the request never reached winfs.
  Stall is on the **CD→winfs inbound leg** (CD didn't deliver, or the inbound
  stdin pipe stalled). winfs can do nothing; → upstream report.
- **`RECV <id>` present, no `SEND <id>`** → winfs received but never produced a
  response. This would **contradict P3** (impl is fast). Re-open a winfs-side
  investigation of that specific request.
- **`RECV` + `SEND` present, small `duration-ms` (< ~250 ms), but `t4`
  (CD-receive) is ~240 s after `t3` (winfs SEND)** → winfs did its job fast;
  the stall is on the **winfs→CD outbound leg** (outbound stdout pipe stalled,
  or CD didn't read the response in time). This is the most likely outcome
  given P3. → upstream report; note any size correlation (does it only happen
  above N bytes?).
- **No hang reproduces with logging on** → Heisenbug: the sync-flush logging
  changed timing enough to mask it. That itself is evidence the hang is
  timing-sensitive (consistent with a transport race). Document and stop.

## Phase F — instrumentation is off by default

`WINFS_TRANSPORT_LOG` defaults to **unset** → `createTransportLogger` returns
`null` → the transport is never wrapped → zero overhead and no behavior change.
Documented in `README.md` and `CLAUDE.md` operational notes. The logger ships
so any future recurrence can be captured immediately, but never runs unless
explicitly enabled.
