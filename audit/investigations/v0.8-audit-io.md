# v0.8 P3 — audit IO investigation report

**Date:** 2026-05-22
**Wave:** v0.8.0 backlog item P3 (escalated to do-before-P5)
**Result:** Recommendation **§5(d) "P5 not justified — root cause environmental"**
**Reproducer for session 4-minute hang:** NOT reproduced.

## 1. Methodology

### 1.1 Hypothesis

The session-observed pattern was: `winfs:write` on 10–13 KB payloads
appeared to hang for 4 minutes during prompt-writing, while
`Filesystem:write_file` on the same payloads completed in <1 s on the
same machine. Two candidate explanations:

- **Atomicity overhead.** winfs:write uses temp + fsync + rename
  (3 syscalls); Filesystem uses raw `fs.writeFile` (1 syscall). On
  Windows-NTFS the rename is fast but fsync is not free.
- **Audit IO.** winfs:write appends a JSONL record to the audit log on
  every mutation; Filesystem doesn't.

The benchmark isolates each contribution to localize where time is
actually spent.

### 1.2 Scaffold

`scripts/perf/audit_io_investigation.mjs` runs three variants:

| Variant | Validation | Atomic write | Audit append |
|---|---|---|---|
| **A_full**     | yes (checkAllowed) | yes (atomicWriteFile = temp+fsync+rename) | yes (fire-and-forget appendAudit) |
| **B_no_audit** | yes                | yes (same atomicWriteFile)                | NO |
| **C_raw**      | yes                | NO (single fs.writeFile)                  | NO |

`A - B = audit contribution to wall-clock`.
`B - C = atomicity contribution to wall-clock`.

Sub-phase timestamps captured with `performance.now()` at:

| Mark | Point |
|---|---|
| t0 | handler enter |
| t1 | path validation complete (checkAllowed returned) |
| t2 | pre-write (after UTF-8 encode) |
| t3, t4 | inside / after atomicWriteFile (combined — `atomicWriteFile` does temp+fsync+rename as one call, so t3 ≈ t4) |
| t5 | after audit-entry enqueued (`appendAudit` returns — fire-and-forget) |
| t6 | handler return |

Note: t3_t4_rename consistently reports 0 ns because the call boundary
is INSIDE `atomicWriteFile`. The full temp+fsync+rename cost is
captured by `t2_t3_write` (= the duration of the `atomicWriteFile`
call) — see "Section 2.3" for the decomposition discussion.

### 1.3 Payloads + iterations

5 payload sizes: 1 KB, 10 KB, 100 KB, 1 MB, 10 MB. Same payload bytes
across variants (printable ASCII repetition pattern; no surrogate edge
cases).

5 warmup iterations (discarded) + 30 measured iterations per
(variant × size). Each iteration writes to a fresh path inside a
disposable temp directory.

Hard limit: 60 s per iteration. Any iteration exceeding the limit
records `INF` in CSV; flagged in summary.

### 1.4 Environment

- Host: Dell Precision 3560 (User account), Windows 10 Pro 10.0.19045
- Node: v24.15.0
- winfs: main @ v0.8.0 (commit e5a7f3c at bench time)
- Temp dir: `$env:TEMP\winfs-bench-<random>` (typically NTFS on internal SSD)

## 2. Results

### 2.1 Total wall-clock per write (t0..t6), mean of 30 iters

| Size  | A_full (ms) | B_no_audit (ms) | C_raw (ms) |
|-------|-------------|-----------------|------------|
| 1 KB  |    1.93     |     1.71        |   0.96     |
| 10 KB |    2.61     |     2.56        |   1.22     |
| 100 KB|    2.82     |     3.00        |   1.28     |
| 1 MB  |    5.49     |    11.85        |   3.33     |
| 10 MB |   29.60     |    33.76        |  19.72     |

INF count across all (variant × size × iter) cells: **0**. No iteration
exceeded the 60 s hard limit.

### 2.2 Component contributions (mean delta)

| Size  | A − B (audit, ms) | B − C (atomicity, ms) |
|-------|-------------------|------------------------|
| 1 KB  |       0.22        |        0.76            |
| 10 KB |       0.05        |        1.34            |
| 100 KB|      −0.18        |        1.72            |
| 1 MB  |      −6.36        |        8.52            |
| 10 MB |      −4.16        |       14.04            |

Negative A − B values at 100 KB / 1 MB / 10 MB are pure noise — the
audit append is fire-and-forget and contributes ~50 µs of synchronous
work (per t4_t5_audit sub-phase). At the totals' scale, OS-scheduler
jitter on the underlying `atomicWriteFile` call dominates the delta.

### 2.3 Where time goes inside A_full at 10 KB

| Phase | Duration (ms) | What it is |
|---|---|---|
| t0_t1_validation | ~0.51 | checkAllowed: realpath + allowed-roots prefix check |
| t1_t2_encode     | ~0.05 | `encodeUtf8NoBom` (string → Buffer) |
| t2_t3_write      | ~2.00 | `atomicWriteFile` end-to-end — open tmp + writeFile + fsync + close + rename |
| t3_t4_rename     | 0     | (rename is INSIDE atomicWriteFile; this delta is always 0) |
| t4_t5_audit      | ~0.05 | `appendAudit` enqueue cost (a `.then(...)` chain push) |
| t5_t6_return     | 0     | dead time |
| **Total t0..t6** | **~2.61** | |

`atomicWriteFile` is the dominant cost (~77 % of total at 10 KB).
That cost is the unavoidable fsync syscall — the rest (open, write,
rename) is nanosecond-class on NTFS.

## 3. Bottleneck localization

### 3.1 At the session-relevant 10 KB size

- Audit contribution: **0.05 ms** (~2 % of total).
- Atomicity contribution: **1.34 ms** (~51 % of total — fsync dominates).
- Total: **2.61 ms**.

**Conclusion at 10 KB:** the entire winfs:write impl finishes in **2.6 ms**
wall-clock. The reported 4-minute session hang is ~92 000× slower than
the impl can possibly take. The hang cannot be explained by either
audit IO or atomicity overhead at this payload size.

### 3.2 At 10 MB

- Audit contribution: negative/noise (still ~50 µs synchronous).
- Atomicity contribution: 14 ms — measurable, ~70 % of the difference
  between A_full (29.6 ms) and C_raw (19.7 ms).
- Total A_full at 10 MB: **29.6 ms**.

Even at 10 MB — well above any realistic prompt payload — winfs:write
completes in 30 ms.

### 3.3 The "Filesystem MCP is faster" observation, partially explained

C_raw at 10 KB: 1.22 ms. winfs A_full at 10 KB: 2.61 ms. **Atomic write
overhead is real (~2× cost) but absolute difference is ~1.4 ms.**
Filesystem MCP being "<1 s" on a payload winfs takes "4 minutes" on is
not explained by the 1.4 ms delta. Filesystem MCP being ~10× faster on
the 10 KB payload (1 ms vs winfs's 2.6 ms) is fully explained by
single-syscall vs temp+fsync+rename.

## 4. Reproducer for the session hangs

**NOT REPRODUCED.** 0 of 30 iterations × 5 sizes × 3 variants = 0/450
hit the 60 s hard limit. p99 wall-clock at 10 MB (A_full) was **42 ms**.

This matches the pattern from bug #1 (EPERM_ROOT post-error hang;
v0.7.1) and bug #2 (silent stdout; v0.7.1/v0.7.2): **the symptom does
not reproduce against winfs source code**. The session-observed
4-minute hang must localize to the MCP transport layer between
Claude Desktop / Claude.ai and the winfs server process, not to
winfs source code.

Pattern reference: `CLAUDE.md` operational note describes occasional
4-minute MCP transport stalls (2-3 four-minute timeouts on the same
call, then the next call returns instantly). This is consistent
with the session observation that prompted this investigation.

## 5. Recommendation

### **§5(d) "P5 not justified — root cause environmental"**

The backlog item P5 (opt-in non-atomic write mode, matching
Filesystem MCP's `fs.writeFile` style) was conceived as a possible
mitigation if atomic-write overhead were the cause of session hangs.
Benchmark data rules out atomic-write overhead as a meaningful
contributor at the relevant payload sizes (1.34 ms at 10 KB; 14 ms
at 10 MB). The 1.4–14 ms savings P5 would offer cannot meaningfully
help workloads that are observing 4-minute hangs.

**Close P5 permanently as not-justified.** Re-open only if a future
benchmark (or production telemetry) shows atomicity contribution
exceeding some operator-defined threshold (e.g. >100 ms at a payload
size used in steady-state — well above any data here).

### Next investigative step (separate from this wave)

MCP traffic-log investigation: capture the JSON-RPC bytes flowing
between Claude Desktop and the spawned winfs process during a
reproducible hang, time-stamped at the wire boundary. If those logs
show the request reaching winfs and a response being produced
quickly, the hang is downstream (transport / client display).
If the request never reaches winfs, the hang is upstream (transport /
client write buffer / MSIX virtualization).

Tooling for that investigation lives outside winfs source code; it's
operator work (Claude Desktop logs + Wireshark on the stdio pipe, or
an MCP-protocol-aware sniffer). Out of scope for this wave; capture
as a separate prompt if Vladimir wants to pursue.

### No code change ships from this wave

Per the investigation contract: scaffold + report only. No production
source changes. Smoke harness re-run after this wave confirmed
66/66 probes still green (we touched only scripts/perf/ and
audit/investigations/).
