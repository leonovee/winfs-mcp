### P1 findings

**P1-1 — Deadline race at maxTimeoutMs is unmitigated (grep.ts:356–359)**

When `resolveTimeoutMs` returns `config.maxTimeoutMs` (e.g. user passes `timeout_ms = 60000` and
`config.maxTimeoutMs = 60000`), the registration block computes:

```typescript
const outerDeadline = Math.min(innerDeadline + OUTER_TIMEOUT_BUFFER_MS, config.maxTimeoutMs);
// = Math.min(60000 + 2000, 60000) = Math.min(62000, 60000) = 60000
```

`innerDeadline === outerDeadline === 60000`. Two independent `setTimeout` calls with the same
wall-clock target race. Node.js event-loop timer ordering is non-deterministic at equal expiry:
whichever fires first determines the outcome. If the outer wrapper's `withTimeout` timer fires
first, the user receives `ETIMEDOUT` (an error) instead of `{truncated: true, reason: "timeout"}`
(a partial result). This violates the spec invariant stated in the review prompt:
"Inner is set 2 seconds shorter than outer so it always fires first."

The spec-correct fix is to clamp `innerDeadline` to `config.maxTimeoutMs - OUTER_TIMEOUT_BUFFER_MS`
before passing it to `grepImpl`, not to clamp the outer deadline downward. Concretely:

```typescript
const innerDeadline = Math.min(
  resolveTimeoutMs(args.timeout_ms, config.defaultTimeoutMs, config.maxTimeoutMs),
  config.maxTimeoutMs - OUTER_TIMEOUT_BUFFER_MS,   // ensure inner always fires 2s before outer
);
const outerDeadline = innerDeadline + OUTER_TIMEOUT_BUFFER_MS;  // always <= maxTimeoutMs by construction
```

This preserves default behavior (10s inner → 12s outer, clamped to max) and never exceeds
`maxTimeoutMs` because `innerDeadline` is already capped at `max - 2000`.

Impact: reproducible at `timeout_ms = maxTimeoutMs` (or when user omits `timeout_ms` and
`defaultTimeoutMs === maxTimeoutMs`). Race is 50/50 at equal fire times in Node.js.

**P1-2 — `re` is stateful (`lastIndex`) when `g` or `y` flag is user-injected via embedded flags (grep.ts:209–215, searchFile:133, searchFileFull:176)**

The regex is created with `new RegExp(args.pattern, flags)` where `flags` is `""` or `"i"`.
However, JavaScript allows embedded flag syntax inside the pattern itself: `(?g)` is not valid
but `(?s)`, `(?m)`, `(?d)` are in newer V8. More critically, a user who passes a raw pattern
string that the grep description says is "JavaScript-flavoured regex source" may expect to
include `(?gimsuy)` via inline flags. V8 ≥ Node 18 supports inline `(?flags:...)` syntax.

The **concrete hazard** is the `g` flag path. If the user passes a pattern such as
`(?:foo)` with `g` intention — currently blocked — but more subtly: the code calls
`re.test(line)` in a loop. `re.test` advances `RegExp.lastIndex` when the `g` or `y` flag is
set. Since the same `re` instance is shared across ALL calls to `searchFile` /
`searchFileFull` across ALL files in the walk, a sticky regex with accumulated `lastIndex`
from file N will cause false negatives on file N+1.

Reproduction: supply `pattern = "foo"` with `case_sensitive = false` (gets `"i"` flag — safe).
But if the pattern were compiled with `g` (not currently possible via the API), every second
`re.test(...)` on a match returns `false` due to `lastIndex` advancement, causing every other
match to be dropped.

The current API surface does not expose `g`/`y`/`u` flags, so this is latent rather than
immediately exploitable. **However**, the description string at line 314 says "JavaScript regex
source", which may invite future flag-pass-through additions that would introduce the bug
without a test catching it.

Recommended mitigation: add a `re.lastIndex = 0` reset at the top of the inner loop
(line 130 in searchFile, line 172 in searchFileFull) as a defensive invariant, and add an
explicit comment that `g`/`y` flags must never be added. Cost: one line per loop.

**P1-3 — `next_offset` computation is wrong when `allMatches` is capped by timeout (grep.ts:286)**

```typescript
const nextOffset = offset + page.length < totalMatches ? offset + page.length : undefined;
```

`totalMatches` is the count of matches collected before the walk aborted (timeout or ceiling).
When `truncated === true` due to timeout, `allMatches` is a partial enumeration. The `page`
is sliced from this partial set. If `offset + page.length < totalMatches` is false only because
the partial scan happened to stop exactly at `offset + page.length`, `next_offset` is `undefined`
even though more files were never scanned.

More precisely: a caller who receives `{truncated: true, reason: "timeout", next_offset: undefined}`
cannot distinguish "this was the last page" from "the scan timed out before finding more
matches". The spec comment at line 19–20 says `total_matches_capped: true` signals the count
is a lower bound — but `total_matches_capped` is only set on CEILING hits (line 232, 273),
NOT on timeout. So a timeout-truncated response with `next_offset: undefined` is
semantically ambiguous: is it the last page, or was the timeout the reason no `next_offset`
was produced?

Fix: when `truncated === true && reason === "timeout"`, always set `next_offset` to
`offset + page.length` (or surface a separate `scan_incomplete: true` field) so callers
know to re-query. Alternatively, always set `total_matches_capped: true` on timeout
as well as on ceiling, since both make `total_matches` a lower bound.

### P2 findings

**P2-1 — Silent skip of unreadable / binary / non-UTF-8 files with no counter surfaced (grep.ts:119–126, searchFileFull:161–168)**

Both `searchFile` and `searchFileFull` swallow all read errors and skip binary / invalid-UTF-8
files silently. The caller sees no signal. On Windows, EBUSY (file locked by another process),
EPERM (ACL deny), and reparse-point errors are all common and actionable.

The review prompt (Q3) flags this explicitly. A clean addition without breaking existing
consumers:

```typescript
// In GrepResult interface and OutputShape:
files_skipped_binary?: number;
files_skipped_unreadable?: number;
```

Both counters default to `undefined` (absent) when zero, preserving backward compatibility.
`files_skipped_unreadable` should arguably be surfaced even as 1 because EPERM silently
hiding files the user asked to search is a trust issue.

**P2-2 — Windows path case-sensitivity in `matchGlob` vs `isInsideAllowed` asymmetry (glob.ts:158–161, walk.ts:70–78)**

`matchGlob` at `glob.ts:159` normalizes the path but does NOT lowercase it before applying
the regex. However, `compileGlob` at line 147 compiles the regex with the `"i"` flag on
`win32`, so the match itself is case-insensitive. This is correct.

`isInsideAllowed` at `walk.ts:70–78` lowercases both sides explicitly before comparison.

The asymmetry is safe in isolation, but it means `matchGlob` relies on the regex `"i"` flag
while `isInsideAllowed` relies on `.toLowerCase()`. If a future refactor removes the `"i"` flag
from `compileGlob` without updating `matchGlob`, Windows paths with mixed case would fail
to match their own glob. Suggest adding a comment to `compileGlob`'s regex construction line
cross-referencing `matchGlob`'s case-insensitivity dependency.

**P2-3 — `searchFileFull` is near-identical to `searchFile` — code duplication risk (grep.ts:110–187)**

`searchFileFull` (pagination path) duplicates `searchFile` (legacy path) in ~40 lines.
They differ only in:
- `searchFile` applies `remaining` as a per-file match cap (line 118, 131)
- `searchFileFull` applies `remainingToCeiling` as a global ceiling cap (line 174)

The `grepImpl` function uses `searchFileFull` exclusively (line 259). `searchFile` is now dead
code — it is defined but never called in the v0.7 surface.

Risk: bugs fixed in one function may not be fixed in the other. The `re.lastIndex` mitigation
from P1-2 would need to be applied to both functions independently. The `files_skipped_*`
counter from P2-1 would need to be added to both independently.

Recommended action: remove `searchFile` or clearly mark it `@deprecated` with a comment
explaining it is kept only for tree-shaken unit test import compatibility.

**P2-4 — `total` field in output is redundant / misleading (grep.ts:293)**

```typescript
return ok({
  matches: page,
  total: page.length,   // <-- always === matches.length
  ...
  total_matches: totalMatches,
```

The `total` field (legacy, from v0.6) equals `page.length` always. The new `total_matches`
carries the meaningful count. Callers who wrote `result.total` to mean "how many matches in the
whole search" are now silently reading the page size. The field name collision creates a
documentation trap. Consider deprecating `total` in the tool description and pointing callers
to `total_matches`.

**P2-5 — Regex DoS: no per-line length pre-check (grep.ts:133, searchFileFull:176)**

As noted in review prompt Q2: catastrophic backtracking on patterns like `(a+)+b` is
unmitigated. The `signal.aborted` check is between lines, not within a single line's regex
evaluation. A 100 KB minified JS line (common on Windows project dirs) with a backtracking
pattern can lock V8 for minutes.

No pure-JS solution fully solves this without an external library (safe-regex, vuln-regex-detector).
Practical mitigations available without dependencies:
1. Add a per-line character length guard: skip lines over N chars (e.g. 4096) with an
   optional `files_skipped_long_line` counter, and document this as a hard limit.
2. Document the limitation explicitly in the tool description so callers are not surprised.

Currently neither mitigation is present. The tool description at line 313 says "JavaScript
regex source" with no DoS caveat.

### P3 findings

**P3-1 — `offset` validation is duplicated between Zod schema and `grepImpl` (grep.ts:50–55, 225–229)**

Zod schema at line 53 marks `offset` as `.nonnegative()`. `grepImpl` at line 225 re-checks
`offset < 0 || !Number.isInteger(offset)` for "defense-in-depth". The comment is correct
(bypassing schema via direct call). But `!Number.isInteger(offset)` for an integer already
checked by Zod is redundant when called through the registered tool path. Low cost to keep,
but the comment should be explicit that `Number.isInteger` is guarding against float values
since Zod `.int()` + `.nonnegative()` does NOT reject `0.5` at runtime if the schema is
bypassed (Zod `.int()` does check for non-integer values, so this is belt-and-suspenders
which is fine — just worth noting).

**P3-2 — Tool description refers to `(?m)` / `(?s)` embedded flags, which are V8 version-dependent (grep.ts:315)**

```typescript
For multiline / dotall semantics use embedded \`(?m)\` /
\`(?s)\` flags inside the pattern itself.
```

Inline `(?s)` (dotAll) as an embedded flag group is a V8/Node 18+ feature. On older Node
runtimes it throws. This is unlikely to matter in practice but the description should note
the Node version requirement, or the code should detect and error gracefully.

**P3-3 — `max_matches` description calls itself a "legacy alias" but `OutputShape` still exposes `total` (legacy field) without a deprecation notice (grep.ts:48, 84)**

Minor documentation consistency gap: `max_matches` is marked "Legacy alias" in its `.describe()`,
but the output field `total` (which is also legacy) has no `@deprecated` marker in either
the interface comment or the Zod `OutputShape`. Both should be consistently marked.
