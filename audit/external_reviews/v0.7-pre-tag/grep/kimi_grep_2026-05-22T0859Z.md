**Confirmed REAL BUG findings after triage:**

P1 (3 confirmed):

[B1] Deadline race at timeout_ms = maxTimeoutMs
grep.ts lines 348-359 (outerDeadline formula in registerGrepTool)
Formula: outerDeadline = Math.min(innerDeadline + 2000, maxTimeoutMs). When innerDeadline
equals maxTimeoutMs, both timers fire at the same wall-clock instant. The outer runTool
wrapper may win, returning ETIMEDOUT error instead of the expected partial-result
{truncated:true, reason:"timeout"} response. Non-deterministic failure.
Reproduction: config.maxTimeoutMs=10000, send {timeout_ms:10000}.

[C1] ReDoS — catastrophic backtracking hangs one line's evaluation
grep.ts line 133 (re.test(line) inside searchFile/searchFileFull)
The abort signal is checked BETWEEN lines but a single line's regex.test() runs to completion.
Pattern "(a+)+$" on a 10000-char line of 'a' can stall V8 for minutes despite the deadline.
Reproduction: {pattern:"(a+)+$", path_glob:"/allowed/**"}, file: 10000 x 'a' on one line.

[F3] context_lines = -1 bypasses impl-level check
grep.ts lines 136-139 (searchFile), lines 178-183 (searchFileFull)
No defense-in-depth guard for negative context_lines inside grepImpl. Math.max(0, i-(-1))
= i+1, so before-context window expands by one extra line per match. Zod guards the
registered tool path; internal callers (unit tests, future tools) bypass this.
Reproduction: call grepImpl directly with {context_lines:-1}.

P2 (7 confirmed):

[A4] Full scan before slice — O(TOTAL_MATCH_CEILING) memory always allocated
grep.ts lines 230-277 (searchFileFull accumulates into allMatches before sort+slice)
Pattern ".*" with limit=1,offset=9999 on a 10000-line file causes all 10000 Match objects to
be loaded into allMatches before the slice(9999, 10000). ~5MB worst case. DoS vector for
repeated requests from untrusted callers.

[A6] next_offset misleading when totalMatchesCapped=true
grep.ts lines 284-289 (nextOffset formula)
When ceiling hit, totalMatches=10000 is a LOWER BOUND. A caller with offset=9995,limit=10
gets next_offset=10005. But the scan stopped at 10000; position 10005 was never checked.
The caller iterates to page starting at 10005, gets {matches:[], total_matches:X}, and must
infer termination. Pagination chain silently dead-ends rather than explicitly stating so.

[C4] Pattern matching literal \r on CRLF files returns no matches
grep.ts line 128 (lines = text.split(/\r?\n/))
The split regex strips \r before \n. A search for \r finds nothing in CRLF-encoded files
even though \r characters are present in the raw file. The match.match text also loses \r.
Reproduction: {pattern:"\r"}, CRLF file.

[D2] Bare \r line endings (old Mac format) treated as single line
grep.ts line 128 (split(/\r?\n/) does not split on bare \r)
An old Mac-format file with \r-only line endings is treated as one giant line. Pattern
matching works but line numbers are all 1, and context_lines has no effect. Unlikely in
practice but testable.

[D4] 10MB single line stored in match.match with no cap
grep.ts line 134 (match: line)
No per-line length limit. A file with a single 10MB line produces a Match object with a 10MB
match.match string. With context_lines>0, context arrays contain the same 10MB string.
Full allMatches accumulation then sorts and slices these. Memory pressure DoS vector.

[E1] Wildcards-only glob may produce empty base, bypassing checkAllowed
grep.ts line 204 (checkAllowed(compiled.base))
If compileGlob("**/*.ts") returns base="" or base=".", checkAllowed receives an empty or
relative path. Behavior depends on compileGlob (not in scope here). If checkAllowed with an
empty path does not reject, the walk would proceed from the process working directory.
Candidate P1 pending compileGlob source review.

[H2] truncated=false but total_matches_capped=true — completeness invisible to callers
grep.ts lines 232-233, 286-289
When TOTAL_MATCH_CEILING=10000 is hit with no timeout and no page overflow, truncated stays
false and reason is absent. A caller checking only truncated considers the result complete.
The total_matches_capped flag is the only signal, but callers not reading the spec miss it.
