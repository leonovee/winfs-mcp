# v0.9.2 security audit — triage & exposure assessment

**Date:** 2026-06-02
**Baseline:** `main @ 58c8a75`, 490 tests green, 72/72 smoke green.
**Tooling:** Node v24.15.0, npm 11.12.1.
**Raw audit:** `audit/security/npm-audit-2026-05-22.json`

`npm audit` reported **7 vulnerabilities (1 low, 5 moderate, 1 critical)**.

## Framing

An npm-audit severity is the CVE's severity *in the abstract*, not winfs's
actual exposure. winfs ships only what `package.json#files` lists
(`dist/`, `README.md`, `CHANGELOG.md`, `configs/`) and runs exclusively over
**`StdioServerTransport`** (`src/index.ts:55`) — no HTTP listener, no dev
server. Runtime dependencies are just three: `@modelcontextprotocol/sdk`,
`diff`, `zod`. Everything else in the tree is dev/test tooling, not shipped.

Exposure classes used below:
- **EXPOSED** — winfs runtime can hit the vulnerable path with attacker-influenced input.
- **LOW** — reachable only with trusted input, or via a code path winfs never calls.
- **DEV-ONLY** — test/build tooling, not present in the shipped `dist/`.

## Per-vulnerability triage

### 1. vitest — CRITICAL — `GHSA-5xrq-8626-4rwp` → **DEV-ONLY (exposure NONE)**

- "When Vitest UI server is listening, arbitrary file can be read and executed."
- **devDependency** (`vitest ^2.1.8`, installed `2.1.9`). Not in `files` → never shipped to npm consumers.
- The vulnerable path requires the **Vitest UI server** to be listening (`--ui` / `--api`). winfs runs `vitest run` (one-shot, no UI, no API socket). The UI server is never started.
- Transitive dependents (`@vitest/mocker`, `vite`, `vite-node`) all hang off this same dev-only test framework.
- Fix: `vitest@4.1.8` (MAJOR, 2.x → 4.x).
- **Verdict: real runtime exposure NONE.** Bumped anyway in Phase D because the migration proved clean (closes the critical + 4 transitive moderates in one move).

### 2. @vitest/mocker — MODERATE → **DEV-ONLY (NONE)**
Transitive under vitest. Not shipped. Closed by the vitest@4 bump.

### 3. vite — MODERATE → **DEV-ONLY (NONE)**
Transitive under vitest / @vitest/mocker / vite-node. winfs never runs a vite dev server. Closed by the vitest@4 bump.

### 4. vite-node — MODERATE → **DEV-ONLY (NONE)**
Transitive under vitest. Not shipped. Closed by the vitest@4 bump.

### 5. esbuild — MODERATE — `GHSA-67mh-4wv8-2f99` → **DEV-ONLY (NONE)**
- "esbuild enables any website to send any requests to the development server and read the response."
- The flagged instance is `esbuild@0.21.5` pulled by `vite` (`<=0.24.2`). winfs never runs the esbuild/vite dev server. (`tsx`'s own `esbuild@0.28.0` is already above the vulnerable range and not flagged.)
- Closed by the vitest@4 bump (which pulls vite≥6 → esbuild>0.24.2).

### 6. qs — MODERATE — `GHSA-q8mj-m7cp-5q26` → **LOW (unreachable at runtime)**
- "qs.stringify crashes with TypeError on null/undefined entries in comma-format arrays when `encodeValuesOnly` is set" (remotely triggerable DoS).
- Transitive: `@modelcontextprotocol/sdk → express@5.2.1 → (body-parser →) qs@6.15.1`.
- express is part of the SDK's **HTTP/SSE transport**, which winfs **does not use** — winfs is stdio-only, never instantiates express, never starts an HTTP listener. `qs` is never invoked at winfs runtime. Even if it were, the crash is in a specific `qs.stringify` comma-array serialization path, not express's query-string `qs.parse`.
- **Verdict: runtime exposure NONE.** Fix is non-breaking, so applied in Phase C at zero cost.

### 7. diff — LOW — `GHSA-73rr-hh4g-fpgx` → **LOW (unreachable code path)**
- "jsdiff has a Denial of Service vulnerability in `parsePatch` and `applyPatch`."
- Direct **runtime** dependency (`diff ^7.0.0`, installed `7.0.0`).
- winfs imports only `createPatch` (`src/tools/editor/edit_file.ts:3,272`) and `createTwoFilesPatch` (`src/tools/slicing/diff_files.ts:4,174`) — both **patch *generation*** from two known texts. The vulnerable `parsePatch` / `applyPatch` (patch *parsing/application* of an untrusted patch string) are **never called** anywhere in `src/`.
- **Verdict: real exposure NONE** (vulnerable functions unreachable). Fix is `diff@9.0.0` (MAJOR); attempted in Phase D and kept because `createPatch`/`createTwoFilesPatch` are API-stable across the bump and all 490 tests stayed green.

## Final state

All 7 vulnerabilities **RESOLVED**. `npm audit` after the wave reports
**0 vulnerabilities**. Verification at the close of the wave:

- `npm audit` → 0 vulnerabilities (was 7: 1 low / 5 moderate / 1 critical)
- `npm test` → 490 passed (under vitest 4.1.8)
- `npm run build` → clean (tsc)
- `node scripts/smoke/v0.7-smoke.mjs` → 72/72 probes green

**Residual vulnerabilities: none.** Nothing was deferred — every finding was
closed by a clean, non-breaking-to-the-shipped-runtime change:
- `qs` via a semver-compatible patch (Phase C);
- `diff` via an API-stable major bump (the only runtime-dep fix; Phase D);
- the vitest cluster (critical + 4 moderates) via a dev-only major bump whose
  one cost was a mechanical test-signature migration (12 `describe` blocks),
  not a winfs source change (Phase D).

Notes for a future reader:
- The single runtime-shipped fix is `diff` 7 → 9. winfs's two diff call sites
  (`createPatch`, `createTwoFilesPatch`) are unchanged across the bump and are
  pinned by the existing edit_file / diff_files unit tests.
- The critical (vitest) never had real exposure — it is dev tooling and its
  vulnerable UI-server path is not started by `vitest run` — so even before
  the bump the shipped server was not at risk from it.
