# v0.8 backlog — Filesystem MCP parity

Items distilled from a 2026-05-22 comparison of winfs against the
reference `@modelcontextprotocol/server-filesystem` (GitHub `main`
branch on that date). Items listed in priority order — note **P3
escalated** after observation that winfs:write hangs are still
unattributed; without that investigation, any non-atomic-fallback
work (P5) is symptom suppression.

## P1 — MCP Roots protocol support

**Value:** large. Solves an entire class of operational pain that
v0.7 hit repeatedly — config.json edits + Claude Desktop restart cycle
just to add an `allowedRoots` entry. With MCP Roots, the client
(Claude Desktop / VS Code / Cursor) signals its current project roots,
and the server auto-updates `allowedRoots` from that signal without
restart.

**Scope:** medium-to-large feature wave.

**Implementation references** (from the reference filesystem server):

- `RootsListChangedNotificationSchema` subscription to receive updates
  from client during runtime.
- `server.server.oninitialized` hook to fetch initial roots via
  `server.server.listRoots()`.
- `getValidRootDirectories(requestedRoots)` validates and normalizes
  before swapping in.
- Existing static `allowedRoots` from `%LOCALAPPDATA%\mcp-winfs\config.json`
  remains as fallback when client doesn't support roots protocol.

**Design considerations specific to winfs:**

- Audit log entries should include which roots were active at request
  time (roots can change mid-session — auditor needs to know what was
  permitted when).
- Roots from client take precedence over config.json, OR merge with
  config.json — needs design call. Reference server *replaces*; we
  may want *union* given winfs's hard-invariant safety posture.
- Invariant spec section needed: when client roots are provided,
  config.json `allowedRoots` either is ignored or unioned, never
  silently extended.

## P2 — Tool annotations sweep

**Value:** small but free. Each MCP tool registration accepts
`annotations: { readOnlyHint, idempotentHint, destructiveHint }`.
Clients use these to display correct warnings before tool calls.

**Scope:** mechanical sweep across all `register*Tool` callsites.
Estimated 1 commit.

**Procedure:**

- For each tool, classify:
  - `readOnlyHint: true` — read, list, get_file_info, grep, list_path_dirs
  - `destructiveHint: true` + `idempotentHint: false` — write (overwrite mode),
    edit_file, move, append (if not idempotent)
  - `destructiveHint: true` + `idempotentHint: true` — write (overwrite_false),
    create_dir (idempotent by design)
  - `destructiveHint: false` + `idempotentHint: true` — start_process,
    interact (consumers don't expect "idempotent" but they don't mutate FS)
- Verify against reference filesystem server's classifications where they
  overlap.

## P3 — Audit log IO investigation [escalated to "do before P5"]

**Value:** medium-to-high. May explain the systematic winfs:write hang
observed on large payloads (10+ KB prompts). Reference filesystem
server doesn't have audit log; its writes are much faster on the same
machine where winfs:write times out.

**Why escalated:** P5 (configurable non-atomic write opt-in) is the
natural response to "winfs:write sometimes hangs," but applying it
without first knowing whether the bottleneck is audit, atomic write,
MCP transport, or something else is symptom suppression. P3 must
complete (or be ruled out) before P5 starts.

**Scope:** investigation, not feature. Result might be "no action,"
"batched audit flush," or "atomic-write 2-syscall overhead measurable
on 100 KB+ payloads, justifies opt-in non-atomic mode."

**Procedure:**

1. Instrument both code paths with timestamps at: validate-entry,
   pre-write, post-write, audit-entry-flushed.
2. Test on payloads of varying sizes (1 KB, 10 KB, 100 KB, 1 MB).
3. Compare. If audit is the bottleneck, evaluate trade-offs:
   - Batched flush (N writes or M ms whichever first) — reduces IO at
     cost of durability window.
   - Async fire-and-forget (already partially done per CC's wave 2c note)
     — returns to caller before audit committed.
   - Separate audit thread / process — overengineered for current scope.
4. If audit is NOT the bottleneck, look at atomic-write 2-syscall
   overhead, MCP transport JSON framing for large payloads, or
   Claude Desktop transport stalls (the bug #1/#2 environmental cause).
5. Output: investigation report at `audit/investigations/v0.8-audit-io.md`
   with timings, bottleneck localization, and recommendation
   (one of: "no action", "audit flush change X", "P5 justified", "P5
   unjustified — root cause is transport not impl").

## P4 — Small parity items

Individual items, each ~1 commit. Bundle as a single wave or fold into
unrelated waves.

### P4.1 — head/tail params in read

Reference filesystem `read_text_file` accepts `head: N` and `tail: N`.
Currently winfs:read requires `offset` + `length`, which is more
flexible but verbose for common log-inspection cases. Add `head`/`tail`
as convenience inputs that compose to existing offset/length internally.

Mutual-exclusion check: if both `head` and `tail` specified, return
EINVAL.

### P4.2 — directory_tree JSON output

Reference filesystem has `directory_tree` returning recursive JSON
structure `{name, type, children?}`. winfs:list returns flat array
with depth — agent has to reconstruct tree itself. Add a tool that
emits the tree directly; share the same underlying traversal as list.

Configurable `excludePatterns` like the reference.

### P4.3 — list_directory_with_sizes

Reference has `sortBy: 'name' | 'size'`. Useful for storage-cleanup
agents that want to find largest files. winfs:list returns sizes per
entry but no built-in sorting. Add a `sort_by` parameter.

### P4.4 — read_media_file (base64 binary)

Reference's `read_media_file` streams binary content (png/jpg/audio)
through `createReadStream` → chunks → `Buffer.concat` → base64.
winfs:read is text-only. If agent needs to inspect a screenshot or
audio sample without download-to-disk roundtrip, this fills the gap.

Streaming is important — naïve `fs.readFile().toString('base64')` on
large media files blows up the memory.

## P5 — Configurable non-atomic write opt-in [blocked on P3]

**Value:** uncertain until P3 completes. If P3 confirms that the
atomic-write 2-syscall overhead is measurable on large payloads
(and audit is not the dominant bottleneck), then a non-atomic opt-in
makes sense for cases where caller explicitly accepts durability/safety
trade-off.

**Why this is NOT a silent fallback:** the original intuition was
"winfs:write hangs → fall back to raw fs.writeFile transparently."
This is rejected because:

1. Silent fallback **breaks the atomic-write contract** that callers
   depend on. Caller gets `success` without knowing atomicity was
   degraded; if a crash happened during the raw-write window, the
   file is corrupted with no recovery path. Worse than atomic-or-fail,
   because the caller no longer knows the guarantee was upheld.

2. We **do not yet know what hangs**. Three winfs:write timeouts
   observed in 2026-05-22 sessions matched the same 4-minute hang
   pattern as bug #1 (EPERM_ROOT) and bug #2 (silent stdout). Both
   were disproven as winfs source defects — environmental (MCP
   transport / Claude Desktop instance). If transport is the cause,
   a fallback in the impl changes nothing because the request never
   reaches the impl. P3 must localize the bottleneck before fallback
   logic is justified.

3. Filesystem MCP's stability on the same payloads is **not proof
   that atomicity is the issue**. The reference server differs in
   many ways (no audit log, simpler validation, monolithic file with
   smaller code path, etc.). Attributing speed to atomicity-absence
   alone is hypothesis, not data.

**If P3 justifies P5**, the implementation should look like:

- New parameter on winfs:write: `atomic: boolean` (default `true`).
- When `atomic: true` (default): current tmp + fsync + rename path.
  Behaviour unchanged.
- When `atomic: false`: direct `fs.writeFile`. Caller explicitly opts
  in to the safety trade-off; tool description and audit log entry
  both surface that this call was non-atomic.
- Audit entry includes `atomic: false` flag so post-hoc review can
  flag mass non-atomic usage as a smell.
- Spec amendment: the atomic-write invariant for winfs:write is
  conditional on `atomic: true` (default); doc the exact failure
  modes of `atomic: false` (mid-write crash → partial file).

**Alternative if P3 indicates atomic is fast and audit is bottleneck:**
P5 becomes irrelevant. Fix audit instead (batched flush or async).

**Alternative if P3 indicates root cause is transport:** P5 is rejected
permanently. Add operational notes documenting the transport
limitation, possibly chunked-write or wire-protocol-level mitigation
in a separate wave outside winfs server impl.

## Out-of-scope

The following from the reference server are NOT brought in:

- **Default non-atomic write_file** — we keep atomic write (tmp + fsync
  + rename) as the default invariant; the reference's raw `fs.writeFile`
  is faster but unsafe on crash mid-write. Non-atomic remains opt-in
  per P5 (and only if P3 justifies P5 at all).
- **No audit log** — we keep audit for operational visibility; the
  reference's omission is a feature gap we intentionally don't follow.
- **Monolithic single-file structure** — winfs's modular `src/tools/{file,
  search,exec,network,editor,system}/` keeps surfaces independently
  testable; reference's 767-line single file would not scale to our
  surface count.
